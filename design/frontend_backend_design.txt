[총알받이] 프론트엔드·백엔드 서버 설계서
프로젝트명: AI·AR 기반 실내 대피 안내 서비스
영문 가칭: AR Evacuate System
설계 기준: 2026년 11월 23일, 관리자 웹과 로컬 서버 구현 상태

1. 설계 목표와 범위

관리자가 건물·층·방 정보를 등록하고 출입문 사진을 연결하면, 서버가 해당 정보를 보관하고 조회 요청에 응답하는 구조를 설계한다.
이번 단계의 범위는 관리자 웹, 장소·사진 API, 서버 데이터 저장이다. 사용자 Android 앱은 별도 팀원이 개발하며, 실제 휴대폰의 네트워크 연결·대피 경로·AI 기능은 후속 단계다.
본 프로젝트는 아이디어 발표와 모의 안내 시연을 위한 학생 시제품이다.

2. Frontend Design — 프론트엔드 설계

2-1. 사용자와 플랫폼
주 사용자: 공간과 안내 정보를 등록·관리하는 팀원 및 시설 관리자 역할의 시연자.
플랫폼: PC 브라우저 기반 관리자 웹.
기술: React, TypeScript, Vite, HTML/CSS.
프로젝트 위치: admin-web/

2-2. 화면 구성
현재는 여러 메뉴로 분리하지 않고 한 화면을 다음 영역으로 구성한다.

① 서버 연결 상태
- 서버 연결됨·연결 중·연결 실패 표시.
- ‘서버 연결 다시 확인’ 버튼 제공.
- 서버에 연결되지 않았을 때 등록·수정·삭제·사진 저장을 제한.
- 이전 브라우저 데이터가 있으면 서버 복사 안내와 복사 버튼 표시.

② 장소 등록·수정
- 입력 항목: 건물 이름, 층, 방 이름.
- ‘장소 등록’으로 새 장소 생성.
- 목록의 ‘수정’을 누르면 기존 값이 입력창에 표시됨.
- ‘수정 내용 저장’과 ‘수정 취소’ 제공.
- 이름 수정 시 장소 ID를 유지해 사진 연결을 보존.

③ 등록된 장소 목록
- 건물·층·방 이름·수정·삭제 버튼과 활성 장소 개수 표시.
- 삭제 전 확인창 제공.
- 삭제한 장소는 일반 목록과 사진 선택 목록에서 제외.
- ‘삭제한 장소’를 펼쳐 복원 가능. 사진을 영구 삭제하지 않음.

④ 출입문 사진 등록
- 사진을 연결할 장소 선택.
- JPG·PNG·WebP 사진 선택, 최대 15MB.
- 긴 변을 1,600px 이하의 JPG로 줄여 저장 준비.
- 저장 전 미리보기, 사진 저장, 선택 취소 제공.
- 장소마다 사진 한 장을 연결하며, 저장 성공 시 기존 사진을 교체.
- 저장된 파일명·저장 시각·저장 전/저장됨 상태 표시.

2-3. 사용자 흐름
장소 등록: 입력 → 필수 값·중복 확인 → API 요청 → 성공 응답 → 목록 갱신.
사진 등록: 장소 선택 → 파일 선택·형식 확인 → 미리보기 → 사진 저장 → API 성공 응답 → 저장 완료 표시.
장소 삭제: 삭제 선택 → 확인창 → 서버에서 삭제 상태 기록 → 일반 목록에서 제외 → 필요 시 복원.

2-4. 입력과 오류 처리
- 건물·방 이름은 최대 60자, 층은 최대 30자.
- 입력 앞뒤 공백과 연속 공백을 정리.
- 같은 건물·층·방 이름의 활성 장소 중복 방지.
- 파일 선택만으로 저장했다고 표시하지 않음.
- 네트워크·파일·저장 오류를 화면에 설명하고 서버 성공 응답 전에는 저장 완료로 처리하지 않음.
- 처리 중 중복 클릭을 막고 입력창·버튼에 접근 가능한 이름을 제공.

2-5. 주요 소스 역할
App.tsx: 서버 연결, 데이터 복사, 장소 등록·수정·삭제·복원, 목록 표시.
DoorPhotoManager.tsx: 사진 선택·미리보기·저장·장소별 사진 조회.
api.ts: API 요청, 응답 처리, 기존 데이터 서버 복사.
types.ts: 장소 데이터 형식.
photos.ts: 사진 크기 변환과 이전 브라우저 사진 읽기.

3. Design Backend Server — 백엔드 서버 설계

3-1. 역할과 기술
웹에서 전달한 장소·사진을 검증하고 데이터베이스에 저장한다. 저장된 정보를 조회하고 수정·삭제 상태·복원을 처리한다.
기술: Python, FastAPI, Uvicorn, SQLite, Pydantic, Pillow.
프로젝트 위치: server/
현재 실행 주소: http://127.0.0.1:8000
관리자 웹 주소: http://127.0.0.1:5173
Vite가 웹의 /api 요청을 로컬 FastAPI 서버로 전달한다.

3-2. 서버 구성
요청 처리: FastAPI가 HTTP 메서드·경로별 기능을 실행한다.
입력 검증: Pydantic으로 필수 값·문자열 길이·ID·복사 데이터 형식을 검증한다.
사진 처리: Pillow로 실제 이미지 여부를 확인하고 크기를 줄여 JPG로 저장한다.
데이터 저장: Python sqlite3로 트랜잭션을 사용해 저장한다.
기동: Uvicorn이 로컬 서버를 실행한다.

3-3. 데이터베이스 구조
저장 파일: server/data/evacuate.sqlite3

[places — 장소]
id: 장소 고유 ID, 기본 키.
building: 건물 이름.
floor: 층 이름.
room: 방 이름.
building_key / floor_key / room_key: 중복 검사용 정규화된 이름.
created_at: 생성 시각.
deleted_at: 삭제 시각. NULL이면 활성 장소.
제약: 활성 장소의 건물·층·방 이름 조합은 중복 불가.

[photos — 출입문 사진]
place_id: places.id를 참조하는 외래 키이며 기본 키.
name: 선택한 원본 파일명.
content: 검증·변환한 JPG 이미지 데이터(BLOB).
saved_at: 서버 저장 시각.
관계: 장소 하나에 사진은 없거나 한 장 존재한다.

[settings — 서버 설정]
key / value: 설정 이름과 값.
database_id: 데이터베이스를 식별하는 값. 같은 서버에 대한 중복 복사 여부 확인에 활용.

현재 단계에서는 건물·층을 별도 테이블로 분리하지 않고 장소에 문자열로 저장한다. 사진도 하나의 SQLite 파일에 보관해 장소·사진 복사와 백업을 단순화한다.

3-4. 현재 구현 API
GET    /api/status                         서버 연결·데이터베이스 식별 값 확인
GET    /api/places                         관리자 장소 목록 조회(삭제한 장소 포함)
POST   /api/places                         장소 등록
PUT    /api/places/{id}                    건물·층·방 이름 수정
DELETE /api/places/{id}                    장소를 삭제 상태로 변경
POST   /api/places/{id}/restore            삭제 상태 해제
GET    /api/places/{id}/photo              사진 파일명·저장 시각 조회(사진 없으면 null)
GET    /api/places/{id}/photo/content      JPG 이미지 조회
PUT    /api/places/{id}/photo              사진 저장·교체(multipart: file, name)
POST   /api/import                         기존 브라우저 장소·사진 복사

장소 응답 형식:
{
  "id": "고유 UUID",
  "building": "본관",
  "floor": "2층",
  "room": "제3회의실",
  "createdAt": "ISO 형식 시각",
  "deletedAt": "삭제한 장소에만 포함되는 시각"
}

응답과 오류: 등록 성공 201, 조회·수정 성공 200. 없는 장소 404, 이름 충돌 409, 큰 사진 413, 미지원 이미지 형식 415, 잘못된 입력·사진 422 등으로 구분해 웹에서 안내한다.
개발용 API 문서: http://127.0.0.1:8000/docs

3-5. 기존 데이터 복사와 보존
기존 localStorage 장소와 IndexedDB 사진을 읽어 서버에 함께 복사한다.
복사 전 데이터 형식과 사진을 검증한다.
한 트랜잭션으로 처리해 충돌 시 일부만 복사되지 않도록 한다.
같은 ID·사진이 이미 있으면 복사 재시도 시 덮어쓰지 않아 서버의 최신 수정을 보존한다.
브라우저 원본은 이전 상태의 백업으로 남기며, 이후 변경 사항은 서버에 저장한다.

4. 프론트엔드와 백엔드 연결 예시

[장소 등록]
관리자 입력 → React 검증 → POST /api/places → FastAPI 검증 → SQLite 저장 → JSON 응답 → 웹 목록 표시.

[사진 저장]
장소 선택·미리보기 → PUT /api/places/{id}/photo → 서버 이미지 검증·변환 → 해당 장소 ID에 사진 저장 → 저장 시각 응답 → 웹 저장 완료 표시.

[다시 열기]
웹 시작 → GET /api/status 및 GET /api/places → 서버 장소 목록 표시 → 장소 선택 → 사진 정보·JPG 요청 → 사진 표시.

5. 구현 상태와 후속 설계

[구현 완료]
관리자 장소 CRUD, 삭제·복원, 사진 등록·교체·조회, 서버 저장, 브라우저 데이터 복사, 서버 재시작 후 데이터 유지, 서버 연결 실패 안내.

[후속 설계·구현 예정]
① 사용자 Android 앱의 네트워크 연결과 앱용 조회 API.
현재 GET /api/places는 삭제한 장소도 포함하는 관리자용이므로 그대로 사용자 앱의 안내 데이터로 사용하지 않는다. 앱용 데이터 범위·응답 형식은 앱 담당자와 합의한다.
② 이동 지점·통로·비상계단 목적지·차단 상태 데이터 구조와 경로 등록 화면.
③ AI 사진 분석·안내 문구 초안·관리자 승인 흐름.
④ 필요한 경우 로그인과 권한, 배포 환경 구성.
위 항목은 현재 구현된 기능으로 발표하지 않는다.

6. 검증과 현재 한계

임시 DB를 사용하는 API 테스트 6개 통과: 장소·사진 저장과 재기동, 중복·빈 값, 삭제·복원 충돌, 손상 사진의 기존 사진 보존, 복사 재시도·충돌 시 전체 취소, 허용하지 않은 출처의 쓰기 차단.
실제 관리자 웹에서 기존 데이터 복사, 사진 서버 저장·조회, 이름 수정, 삭제 상태 저장, 서버 중단 시 오류·입력 제한, 서버 재시작 후 데이터 유지를 확인했다.
현재 서버는 이 PC의 루프백 주소에서 동작한다. 인터넷 배포·다른 PC·휴대폰 연결·로그인은 아직 구현하지 않았다. 실제 화재 환경의 위치 추적·안전 경로 판단을 검증한 시스템은 아니다.
